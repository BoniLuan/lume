# Lume implementation plan

Status: approved for implementation in a later session  
Last verified: 2026-09-16  
Repository: `BoniLuan/lume`  
Production URL: `https://lume.boniluan.com`

This document is the implementation source of truth for Lume v1. It records the
results of read-only VPS investigation and the decisions approved after planning.
It does not authorize deployment or changes to shared infrastructure without a
separate implementation/deployment task.

## Approved product decisions

- Use MariaDB 11.4 LTS, initially the latest tested 11.4 patch and a pinned image
  digest. Do not use moving `latest` or `lts` tags in production.
- All product content and documentation are in English.
- The initial user timezone is `America/Sao_Paulo`.
- The initial base currency is BRL. Store currency explicitly even though v1
  permits only the user's base currency in accounts and reports.
- Credit cards start as simple liability accounts. Statements, installments,
  closing dates, due dates, interest, and refund linkage are deferred.
- Production is a personal deployment. Public self-registration is disabled by
  default; an operator command bootstraps the user.
- The same repository checkout may be used to operate development and production,
  but Compose project names, credentials, databases, networks, volumes, images,
  and commands must remain separate.
- Initial backup goals are pragmatic: one daily encrypted database dump, a
  documented restore drill, and off-VPS copying when a destination is selected.

## 2. Architecture

Lume is a modular monolith with three long-running production containers:

1. `lume-gateway`: Nginx serving the compiled React application and proxying the
   versioned API.
2. `lume-api`: FastAPI application containing all business modules.
3. `lume-db`: dedicated MariaDB 11.4 database.

The API image also supplies one-shot `lume-migrate` and `lume-admin` services
under a Compose tools profile. V1 has no Redis, message broker, worker, scheduler,
or separate reporting service.

```text
Internet
  -> Cloudflare
  -> boniluan-home Nginx (:80/:443)
  -> web-proxy -> lume-gateway:8080
  -> lume_frontend -> lume-api
  -> lume_backend -> lume-db

Existing Prometheus
  -> vigil-monitoring -> lume-api private /metrics
```

Use Python 3.14 with an exact patch release in the image and CI. Use synchronous
SQLAlchemy and PyMySQL: the expected load does not justify an asynchronous database
stack, and the synchronous path is easier to test and operate. Configure database
pre-ping, connection recycling, pool size 5, and maximum overflow 5. Start with one
Uvicorn worker and change only after measurement.

## 6. Authentication

Use opaque server-managed sessions rather than JWTs. This provides immediate
revocation and avoids JWT refresh/revocation complexity at the current scale.

`POST /api/v1/auth/sessions` accepts credentials and an explicit transport:

- `cookie` for the React application, default;
- `bearer` for a future native client.

Generate a cryptographically random 256-bit token and store only its SHA-256
digest. Return the plaintext once. Reject requests that present both a cookie and
bearer credential.

Browser sessions:

- cookie `__Host-lume_session`;
- `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, no `Domain`;
- 30-day absolute expiry and seven-day inactivity expiry, configurable;
- rotate after login and password changes;
- return a session-bound CSRF token from `GET /auth/session`;
- require `X-CSRF-Token` and exact allowed Origin for unsafe cookie requests.

Future mobile sessions use the same table and opaque bearer token stored in OS
secure storage. Bearer requests do not use CSRF. Session listing and revocation
cover both transports.

Hash passwords with Argon2id. Begin with at least 19 MiB memory, two iterations,
and one lane, then benchmark for roughly 100-250 ms on the VPS. Rehash on login
when parameters change.

Production self-registration is disabled. Supply private one-shot commands to
bootstrap a user and reset a password. Do not build an email reset flow in v1.

## 7. Database and financial domain

Use InnoDB, strict SQL mode, `utf8mb4`, and UTC. Store timestamps as UTC
`DATETIME(6)` and user-entered financial dates as `DATE`. Use UUIDv7 IDs stored as
`CHAR(36)` with ASCII binary collation so dumps remain readable.

All monetary columns are `DECIMAL(19,4)` and all Python values are `Decimal`.
The API serializes amounts as strings such as `"47.9000"`; the browser does not
perform authoritative calculations using JavaScript floating point.

### Users and sessions

`users`:

- id, email, unique normalized email;
- password hash and display name;
- base currency, locale, timezone;
- created/updated/disabled timestamps.

Initial values: English content, BRL base currency, `America/Sao_Paulo` timezone.

`auth_sessions`:

- id and user ID;
- unique token hash;
- transport and optional CSRF hash;
- created, last-seen, idle-expiry, absolute-expiry, and revoked timestamps;
- bounded device label and minimal sanitized metadata.

### Accounts

`accounts`:

- id, user ID, name;
- type: checking, cash, savings, credit card, or other;
- class: asset or liability;
- explicit currency;
- signed opening balance and opened date;
- archived and audit timestamps.

V1 validates that account currency equals the user's base currency.

Balance invariant:

```text
opening balance + income - expense - outgoing transfers + incoming transfers
```

Credit cards are liabilities. Purchases make the balance more negative; payments
are transfers from an asset account and make the liability less negative. UI text
uses "amount owed" rather than exposing a confusing negative sign.

### Categories

`categories` contains id, user ID, name, kind (`income` or `expense`), optional
presentation metadata, archived timestamp, and audit timestamps.

Bootstrap copies versioned default templates into user-owned rows. Do not use
shared global category records. Income and expense transactions require an
applicable category; include "Other income" and "Other expense" defaults.

### Transactions

`transactions` contains:

- id and user ID;
- kind: income, expense, or transfer;
- source account ID;
- nullable destination account ID;
- nullable category ID;
- positive amount;
- description and optional bounded notes;
- effective date;
- optional client request UUID for retry-safe creation;
- optional recurring template/occurrence links;
- voided timestamp and audit timestamps.

Invariants:

- Amount is always positive. Kind determines financial effect.
- Income/expense requires one account and an applicable category and prohibits a
  destination account.
- Transfer requires distinct source and destination accounts and prohibits a
  category.
- Both transfer accounts have the same owner and currency.
- Transfers never count as income, expense, or budget use.
- Voided transactions remain in history but affect no balance/report.
- All referenced records must belong to the authenticated user.

Use composite `(id, user_id)` keys and composite foreign keys where practical so
the database also prevents cross-owner relationships. Add indexes for owner/date,
kind/date, account/date, category/date, destination/date, and void filtering.

### Budgets

Support both an overall monthly limit and optional category limits.

`budget_periods` contains user ID, first day of month, positive total limit,
currency, and timestamps, unique per user/month.

`budget_category_limits` belongs to a budget period and an expense category, with
a positive amount and unique category per period.

Overall use includes active expense transactions in the month. Category use
includes active expenses assigned to that category. Transfers and income are
excluded. Category allocations may exceed the overall limit; warn rather than
reject. No rollover or envelope carry-forward in v1.

### Recurring expectations

Recurring templates are expectations and never count as transactions until the
user records them.

`recurring_templates` contains owner, income/expense kind, default transaction
fields, weekly/monthly/yearly frequency, interval, start/next/end dates, preserved
monthly anchor day, active state, and timestamps.

`recurring_occurrences` contains template, owner, scheduled date, recorded/skipped
status, optional transaction ID, and timestamps, unique per template/date.

Recording an occurrence atomically creates the transaction, records the occurrence,
and advances the next date. Skipping records the decision without creating money
movement. A monthly schedule anchored on the 31st clamps in short months and
returns to the 31st afterward. V1 has no scheduler or automatic insertion.

### Credit-card evolution

V1 stores only the liability account and normal expense/payment transactions.
Later versions may add one-to-one card profiles, statement cycles, statements,
installment plans, interest, and linked refund/reversal records without invalidating
existing transactions.

## 10. Security

- TLS only at the public boundary.
- Opaque hashed sessions, Argon2id passwords, generic login failures, revocation.
- Edge IP rate limit plus application identifier cooldown for authentication.
- Production CORS disabled/empty because web and API are same-origin.
- Explicit development origins only; no wildcard with credentials.
- CSRF token and Origin validation for unsafe cookie requests.
- Owner-scoped queries everywhere; inaccessible IDs return 404.
- SQLAlchemy parameter binding and reviewed parameterized aggregate SQL.
- Separate MariaDB roles: `lume_app` for runtime DML and `lume_migrator` for DDL.
- Production secrets under `/home/luan/.config/lume`, with a 0700 directory and
  0444 files for Compose read-only, file-backed bind mounts. The private parent
  directory prevents other host users from traversing to the files. Prefer these
  mounts over passwords in container environment variables.
- Non-root containers, read-only root filesystems, dropped capabilities,
  `no-new-privileges`, and bounded tmpfs.
- CSP, HSTS, MIME sniffing protection, frame denial, strict referrer policy, and
  restrictive permissions policy.
- No public database, metrics, readiness, migration, or admin interfaces.
- No request/response bodies, auth headers, cookies, passwords, email addresses,
  descriptions, notes, or raw query strings in logs.
- Bounded request sizes, field lengths, page sizes, and timeouts.
- No authenticated response or API data in service-worker caches.

## 13. Production deployment

Build immutable images:

- `ghcr.io/boniluan/lume-api:<git-sha>`
- `ghcr.io/boniluan/lume-gateway:<git-sha>`

Deployment order:

1. Require a reviewed clean commit and passing CI.
2. Take and validate a database backup.
3. Pull immutable images.
4. Validate resolved Compose without printing secrets.
5. Run explicit Alembic migrations using the tools profile.
6. Update API and gateway.
7. Verify private health/readiness and the project gateway.
8. Prepare DNS/certificate/shared-edge work separately.
9. Build a candidate edge image and run `nginx -t` with existing mounts.
10. Expand certificate coverage and recreate only `boniluan-home`.
11. Verify Boniluan, FinPulse, Sitio, Vigil, Relay, and Lume routes.
12. Update `/home/luan/projects/INFRASTRUCTURE.md` with actual allocations.

Never run migrations automatically during API startup. Readiness returns 503 if
the schema revision is missing or stale.

Use expand/migrate/contract changes. MariaDB DDL may auto-commit, so rehearse
risky migrations and do not rely on transactional rollback.

## 14. Backup and restore

Use a matching MariaDB client image and `mariadb-dump --single-transaction` with
routines, triggers, events, and binary-safe output. Compress, checksum, encrypt,
and write into a private directory outside the repository. Copy encrypted dumps
off the VPS once a destination is selected.

Initial targets:

- daily backup;
- 14 daily and 8 weekly copies when automation is introduced;
- approximate RPO 24 hours and RTO 2 hours.

Restore drill:

1. Use a unique isolated Compose project.
2. Start fresh MariaDB with a fresh temporary volume.
3. Restore with stop-on-error behavior.
4. Verify the recorded schema revision.
5. Start the candidate API against restored data.
6. Verify readiness, login, representative balances, budgets, recurrence, and
   ownership isolation.
7. Compare key row counts/checksums.
8. Remove only drill-owned resources.

A copied Docker volume and CSV export are not database backups.

## 20. Acceptance criteria

### Foundation

- A fresh clone follows documented setup successfully.
- Lock files are reproducible, CI passes, and no secret is tracked.

### Database/runtime

- Dev, test, and production state are distinct despite a shared checkout.
- MariaDB has no host port.
- Migrations upgrade an empty database.
- Readiness rejects a missing/stale schema.

### Authentication/ownership

- Passwords are Argon2id hashes and session tokens are stored only as hashes.
- Cookie flags, CSRF, Origin validation, session revocation, and rate limits have
  tests.
- Cross-user object access returns 404 and cannot create cross-owner references.

### Financial correctness

- Amounts remain Decimal/string values across database, API, and client.
- Transfer creation is atomic and excluded from income/expense/budgets.
- Account balances reconcile with fixtures, including liability accounts.
- Voided transactions affect no aggregate.
- Month calculations use `America/Sao_Paulo` dates.

### Budgets/recurrence/reporting

- Overall/category usage reconciles with transaction fixtures.
- Leap-day, short-month, 31st, skipped, and duplicate occurrence cases pass.
- Dashboard totals reconcile with raw transactions.
- Queries are bounded and use appropriate indexes.
- CSV preserves exact amount and date values.

### Web/accessibility

- Quick entry works without horizontal scrolling on a small phone viewport.
- Forms have labels/errors and dialogs manage focus.
- Color is never the only status signal.
- Primary flows pass automated axe and manual keyboard checks.
- Loading, empty, and failure states exist.

### Security/operations

- Production CORS is closed and authenticated responses are not cached.
- Public `/metrics` and readiness return 404.
- Logs contain no supplied credentials, descriptions, notes, or raw queries.
- Existing Prometheus targets remain healthy after adding Lume.
- Restore drill starts a valid API from a fresh restored database.
- Images run non-root with read-only filesystems and dropped capabilities.
- Only the gateway joins `web-proxy`; no Lume host port is published.

### Deployment

- Certificate SAN covers `lume.boniluan.com`.
- Lume landing, login, application, and API operate over HTTPS.
- Boniluan, FinPulse, Sitio, Vigil, and Relay remain healthy.
- Final allocations are documented in `INFRASTRUCTURE.md`.

## 21. Known risks and tradeoffs

- MariaDB 11.4 favors maturity over the newest 12.3 LTS features.
- The single-row transfer model is intentionally simpler than full double-entry
  accounting. Investments, FX, and reconciliation may eventually require postings.
- Liability signs are consistent but require user-friendly labels.
- Refunds must later become explicit linked records; treating them as income would
  corrupt income reporting.
- Opaque sessions cause one database lookup per authenticated request, acceptable
  at the expected scale.
- The API's monitoring-network membership exposes its internal port to other
  containers on that private shared network, but not to the public edge.
- Service workers can make stale deployments confusing; never cache API responses
  and use conservative update behavior.
- No swap increases risk during local builds; prefer CI-built images.
- Prometheus currently uses a Relay-generated overlay, so monitoring integration
  needs a composable source of truth rather than another replacement mount.
- DNS resolution does not establish Cloudflare SSL mode, firewall, or origin policy.
- MariaDB DDL may auto-commit; backup and rehearsal matter more than downgrade
  assumptions.
